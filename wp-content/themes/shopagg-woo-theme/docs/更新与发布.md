# SHOPAGG 主题：更新与发布

## 1. 更新责任边界

主题更新由 `wp-content/plugins/shopagg-app-store` 管理。主题端 `XTS\Autoupdates` 负责登记和兼容 WordPress 更新界面，应用商店插件负责：

- 调用 SHOPAGG 远程 API 获取版本；
- 把更新写入 WordPress `update_themes` transient；
- 通过带 Nonce 的本地 AJAX 下载入口获取授权包；
- 校验/下载临时包；
- 在 WordPress upgrader 中把解压目录归一化为实际安装目录；
- 更新完成后刷新登记的 asset path 和更新缓存。

主题不再使用 `https://xtemos.com/wp-json/xts/v1/download?...` 作为主题包下载地址。部分 XTemos 地址仍服务于预建站点、WPBakery/Image Optimizer 历史插件源或其他兼容接口，不能据此判断主题更新仍走 XTemos。

## 2. 两个必须区分的 slug

| 名称 | 当前值 | 用途 |
| --- | --- | --- |
| 远程资源 slug | `shopagg-woo-theme` | SHOPAGG 服务端查找版本 |
| WordPress stylesheet | `shopagg-woo-theme` | 当前父主题安装目录 |

当前二者相同，但代码有意分别保存：

- `$theme_name = SHOPAGG_WOO_THEME_SLUG`；
- `$stylesheet = get_template()`。

这样远程资源与实际安装目标不会因历史登记或包内目录变化而混淆。内部 `WOODMART_SLUG = woodmart` 只用于兼容和旧登记迁移。

## 3. 主题登记

`inc/classes/class-autoupdates.php` 在 SHOPAGG updater 类存在时调用：

```php
ShopAGG_App_Store_Updater::register_managed_resource(
    'shopagg-woo-theme',
    'theme',
    $resource_id,
    get_template()
);
```

登记保存在 `shopagg_app_store_managed_resources`。首次响应可能先按 slug 登记、资源 ID 为 0；远程返回有效版本后补全 ID。

主题还会一次性迁移旧 `woodmart` 资源登记，并清除 `update_themes` 和主题缓存。不要手工同时保留两个 slug 指向同一主题。

## 4. WordPress 更新键

WordPress theme transient 的 key 必须是实际 stylesheet：

```php
$transient->response['shopagg-woo-theme'] = array(
    'theme'       => 'shopagg-woo-theme',
    'new_version' => '8.5.3',
    'package'     => '本地授权下载入口',
);
```

如果误用 `woodmart`，WordPress 会认为要更新另一个主题，可能新增目录、更新失败或使当前主题仍显示旧版本。

## 5. 发布包目录规范

推荐 ZIP：

```text
shopagg-woo-theme.zip
└── shopagg-woo-theme/
    ├── style.css
    ├── functions.php
    ├── inc/
    └── ...
```

SHOPAGG updater 已实现 `upgrader_source_selection` 归一化，可将不同 ZIP 根目录调整为已登记的主题目录。但发包仍应遵循标准结构，归一化是保护机制，不是包结构随意的理由。

绝对禁止发布：

- ZIP 根目录直接散落主题文件；
- 多套主题目录嵌套；
- 包内顶层为旧 `woodmart` 且未测试归一化；
- `.git`、日志、数据库导出、Token、环境配置；
- macOS `__MACOSX` 等无关文件；
- 缺少 `style.css` 的包。

## 6. 版本号

WordPress 安装版本来自 `style.css` 的 `Version`。服务端发布版本必须严格大于安装版本，使用 PHP `version_compare()` 可比较的格式。

一次发布至少同步：

- `style.css` Version；
- SHOPAGG 服务端 ResourceVersion；
- changelog；
- 若 Core 有变更，`WOODMART_CORE_VERSION` 和 bundled ZIP；
- 文档中版本基线；
- 数据迁移的目标版本。

只改服务端版本而不改 `style.css` 会导致更新完成后仍反复提示；只改 `style.css` 而不发布远端版本则不会出现更新。

## 7. 主题版本迁移

主题更新后，`XTS\Theme::check_version()` 比较 `woodmart_version` 与新 `style.css` 版本，随后调度 `woodmart_scheduled_update`，执行 `woodmart_updated` action 并写回版本。

迁移回调示例：

```php
add_action( 'woodmart_updated', function ( $target_version ) {
    if ( version_compare( $target_version, '8.5.3', '<' ) ) {
        return;
    }

    if ( get_option( 'shopagg_853_migrated' ) ) {
        return;
    }

    // 执行可重复的数据迁移。
    update_option( 'shopagg_853_migrated', 1, false );
} );
```

大数据任务不应在一次 action 中全部完成，应分批或交给 Action Scheduler。

## 8. SHOPAGG 主题核心更新

Core 当前由主题内 `inc/plugins/shopagg-woo-theme-core.zip` 提供最低版本更新对象，目标插件文件为 `shopagg-woo-theme-core/woodmart-core.php`。发布主题时必须确认：

- ZIP 存在且可读；
- 包内目录和主插件文件正确；
- 插件 Header 版本不低于 `WOODMART_CORE_VERSION`；
- 从旧 Core 原地升级成功；
- CPT 在升级期间不会临时消失；
- 主题与 Core 的 API 同步。

插件页的 WPBakery 和 Image Optimizer 仍可能使用 XTemos 远程 ZIP。若要完全由 SHOPAGG 管理，应逐个把资源迁移到应用商店，而不是只改变后台文字。

## 9. 发布流程

1. 冻结目标 commit，确认工作区无日志/密钥；
2. 更新版本和 changelog；
3. 执行 PHP 语法、静态检查和 Markdown 链接检查；
4. 在全新站安装 ZIP；
5. 在旧版站通过 SHOPAGG 远程更新；
6. 验证更新目标仍是 `shopagg-woo-theme`，没有生成 `woodmart` 或双目录；
7. 验证 Core、Woo、构建器和数据迁移；
8. 执行完整商城回归；
9. 服务端上传包、校验 checksum、发布版本；
10. 小范围站点灰度，观察错误率、下载、Cron 和结账；
11. 扩大发布；
12. 保留上一版本包和数据库回滚方案。

## 10. 更新故障定位

### 后台看不到更新

- 检查 SHOPAGG 应用商店是否启用和认证；
- 检查登记 option 是否有 `shopagg-woo-theme`、type `theme`、asset `shopagg-woo-theme`；
- 检查服务端 slug、版本、发布状态和资源类型；
- 清除 `update_themes` transient 后强制检查；
- 确认服务端版本大于 `style.css` 版本；
- 检查 API/WAF/DNS/SSL。

### 下载失败

- 当前用户需要更新主题的权限；
- 本地 AJAX Nonce 是否过期；
- API Token/签名链接是否有效；
- PHP 能否访问远程文件；
- 临时目录和 `wp-content/upgrade` 是否可写；
- 包大小是否超过网络、代理或 PHP 限制；
- checksum/Content-Length 是否匹配。

### 更新后目录错误

- 检查服务端 ZIP 根目录；
- 检查 updater 的 `upgrader_source_selection` 是否执行；
- 检查登记 asset_file；
- 检查是否有另一个更新插件抢先修改 source；
- 用预发布环境复现，不要在生产手工移动活动主题目录。

## 11. 当前代码注意事项

`functions.php` 末尾目前会在每次主题加载时执行三次 `update_option()`，写入历史激活状态。它虽然保证兼容状态存在，但会造成不必要的数据库写入/缓存失效，并把“激活”与真实 SHOPAGG 授权混为一谈。

后续建议迁移为一次性版本迁移或激活 Hook，并让 SHOPAGG 认证状态只由应用商店插件管理。在修改前应审计所有依赖这些 option 的旧逻辑，不能直接删除。
