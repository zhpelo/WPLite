# SHOPAGG 主题：架构与启动流程

## 1. 系统边界

SHOPAGG Woo Theme 是 WordPress 父主题，也是多个组件的协调层：

```text
WordPress
├── shopagg-woo-theme
│   ├── 主题模板与资源
│   ├── 主题设置、Header、Layouts
│   ├── WooCommerce 展示与商城增强模块
│   └── Elementor / WPBakery / Gutenberg 适配
├── shopagg-woo-theme-core
│   ├── 自定义内容类型
│   ├── WXR 导入器
│   └── 主题核心能力
├── shopagg-app-store
│   └── 版本检查、授权下载与安装目录归一化
└── WooCommerce / 页面构建器 / 第三方插件
```

主题负责“组合”和“展示”，SHOPAGG 主题核心提供一部分必须长期存在的数据类型与导入能力，SHOPAGG 应用商店负责发行。诊断时不要默认所有问题都能在主题目录内解决。

## 2. 请求启动顺序

### 2.1 `functions.php`

`functions.php` 是最早的主题入口，依次执行：

1. 根据 `get_template_directory_uri()` 和 `get_template_directory()` 定义路径常量；
2. 定义 XTemos 远程地址、内部 `WOODMART_SLUG` 和 SHOPAGG 资源 slug；
3. 加载基础类：Singleton、API、Config、Layout、Autoupdates、Activation、Notices、Theme、Registry；
4. 创建 `new XTS\Theme()`；
5. 从 `style.css` 读取并定义 `WOODMART_VERSION`。

关键常量：

| 常量 | 用途 |
| --- | --- |
| `WOODMART_THEMEROOT` | 父主题本地绝对路径 |
| `WOODMART_THEME_DIR` | 父主题 URL |
| `WOODMART_CLASSES` | `inc/classes` 路径 |
| `WOODMART_CONFIGS` | `inc/configs` 路径 |
| `WOODMART_API_URL` | XTemos 历史 API 根地址，不是 SHOPAGG 更新地址 |
| `WOODMART_DUMMY_URL` | 预建站点远程资源基址 |
| `WOODMART_SLUG` | 历史兼容标识 `woodmart` |
| `SHOPAGG_WOO_THEME_SLUG` | 应用商店远程资源标识 `shopagg-woo-theme` |

路径常量由当前安装目录动态生成，因此把主题目录改为 `shopagg-woo-theme` 后，绝大多数资源路径会自动适配。内部 slug 不随目录改名。

### 2.2 `XTS\Theme`

`inc/classes/class-theme.php` 的构造过程决定模块加载顺序：

1. `require_core()`：SHOPAGG 主题核心未定义版本常量时，尝试加载主题内开发副本；
2. `dashboard_files()`：加载后台仪表盘与品牌相关文件；
3. `general_files_include()`：加载 helpers、setup、enqueue、主题模块、Woo 模块和第三方集成；
4. `wpb_files_include()`：仅在当前构建器为 WPBakery 且插件已加载时加入字段和适配；
5. `register_classes()`：通过 Registry 创建 notices、layout、api、autoupdates、activation、themesettingscss；
6. `wpb_element_files_include()`：载入 WPBakery 元素映射；
7. `shortcodes_files_include()`：加载短代码渲染；
8. 后台请求额外执行 `admin_files_include()`；
9. 在 `init` 初始化主题选项，并检查版本迁移；
10. 在 `woodmart_scheduled_update` 执行版本升级任务。

这一顺序意味着：

- 依赖 WordPress 核心函数的扩展应挂到相应 Hook，不要在插件文件顶层过早调用主题函数；
- Elementor 集成依赖 `elementor/loaded` 已执行；
- WPBakery 文件只在满足构建器和插件常量时加载；
- 后台类并不保证前台请求可用；
- 版本迁移可能由一次性 WP-Cron 事件延后执行。

## 3. 对象管理

### 3.1 Registry

`XTS\Registry` 是按属性名惰性创建对象的容器：

```php
$api = XTS\Registry::get_instance()->api;
```

它会先寻找 `WOODMART_Api`，再寻找 `XTS\Api`，并缓存实例。新增核心对象时必须确认类文件已先加载，否则 Registry 只会返回空结果。不要把 Registry 当成通用依赖注入容器，它没有构造参数、接口绑定和生命周期配置。

### 3.2 Singleton

继承 `XTS\Singleton` 的类通过 `::get_instance()` 创建，每个子类单独保存实例，并在首次创建时自动调用 `init()`：

```php
final class Example_Module extends XTS\Singleton {
    public function init() {
        add_action( 'init', array( $this, 'register' ) );
    }
}
```

如果类使用 Singleton，构造函数不可直接调用；所有 Hook 注册应放在 `init()`。

### 3.3 Config

`woodmart_get_config( 'css-files' )` 最终由 `XTS\Config` 加载 `inc/configs/css-files.php` 并在当前请求内缓存。配置文件必须 `return` 数据，文件名就是配置名。

现有配置包括 CSS/JS 清单、Header 结构、字体、按钮选择器、商品 hover、兼容插件和 Prebuilt 模板版本。适合用声明式数据表达的功能，优先扩展配置而不是复制加载器。

## 4. 代码分层

| 层 | 主要目录 | 说明 |
| --- | --- | --- |
| WordPress 模板层 | 根目录、`templates/` | 页面模板、循环、Header/Footer 片段 |
| Woo 模板层 | `woocommerce/` | 覆盖 WooCommerce 默认模板 |
| 公共框架层 | `inc/helpers.php`、`inc/functions.php`、`inc/actions.php` | 通用函数、Hook 装配和业务辅助 |
| 模块层 | `inc/modules/` | Header、Layouts、搜索、样式存储、性能、动态标签等 |
| 商城集成层 | `inc/integrations/woocommerce/` | 商城模板标签与功能模块 |
| 构建器层 | `inc/integrations/{gutenberg,elementor,visual-composer}/` | 编辑器控件与元素映射 |
| 后台层 | `inc/admin/` | 主题设置、仪表盘、导入、向导、补丁和资源 |
| 配置层 | `inc/configs/` | 静态映射及发行数据 |
| 核心插件层 | `shopagg-woo-theme-core` 插件 | CPT、导入和主题所需插件能力 |

## 5. 文件加载与子主题边界

主题内部的 `enqueue_files()` 使用父主题路径解析 PHP 模块。复制 `inc/...` 文件到子主题，并不会自动替换父主题模块。可覆盖范围如下：

| 方式 | 是否推荐 | 适用范围 |
| --- | --- | --- |
| WordPress Hook/filter | 推荐 | 行为、参数、输出片段、查询 |
| 子主题 `functions.php` | 推荐 | 站点级 PHP 扩展和资源加载 |
| 子主题 WordPress 模板 | 推荐 | `single.php`、`page.php` 等模板层 |
| 子主题 `woocommerce/` | 谨慎推荐 | WooCommerce 模板覆盖，需持续做版本审计 |
| 站点功能插件 | 推荐 | 与主题无关的数据、接口、定时任务和后台业务 |
| 复制父主题 `inc/` | 无效/不推荐 | 父主题加载器仍指向父主题文件 |
| 直接改父主题 | 平台维护场景 | SHOPAGG 品牌、更新、导入器和通用平台能力 |

## 6. 版本迁移生命周期

`XTS\Theme::check_version()` 比较数据库 option `woodmart_version` 与 `style.css` 版本。版本变化后可能调度 `woodmart_scheduled_update`，再执行对应版本迁移并更新 option。

开发迁移时应满足：

- 可重复执行，不因任务重试破坏数据；
- 在执行前检查旧状态，而不是只依赖版本号；
- 大数据迁移分批处理，避免占满一个 PHP 请求；
- 完成后才写入版本标记；
- 记录可检索日志，并提供失败后的恢复方法；
- 多站点环境明确是按站点 option 还是 network option 执行。

## 7. 外部依赖与加载条件

| 依赖 | 必需性 | 影响 |
| --- | --- | --- |
| WordPress | 必需 | Hook、模板、Options、REST、Cron 基础 |
| SHOPAGG 主题核心 | 必需 | CPT、导入器及核心主题功能 |
| WooCommerce | 商城站必需 | 商品、订单、购物流程和绝大多数增强模块 |
| Elementor | 条件必需 | 选择 Elementor 时加载元素和编辑器集成 |
| WPBakery | 条件必需 | 选择 WPBakery 时加载映射和字段 |
| SHOPAGG App Store | 发布环境必需 | 主题远程更新登记、检查和下载 |
| Action Scheduler / WP-Cron | 功能依赖 | 商城后台任务、提醒、跟踪和版本迁移 |

第三方集成文件多数采用“插件存在才生效”的方式加载。新增集成时同时检查类、函数或常量，并保证插件未安装时无致命错误。

## 8. 阅读一个功能的标准方法

以 Wishlist 为例：

1. 在 `class-theme.php` 找到模块入口；
2. 查看 `inc/integrations/woocommerce/modules/wishlist/` 的 Main/Frontend/Admin 类；
3. 检索模块设置项如何通过 `woodmart_get_opt()` 读取；
4. 检索它注册的 Hook、AJAX action、REST route 和 Cron；
5. 找到对应模板、CSS/JS 配置键；
6. 确认数据保存为 option、post meta、user meta、cookie 还是自定义表；
7. 检查缓存失效和卸载策略；
8. 最后在前台、后台、访客、登录用户和缓存开启状态验证。

不要只阅读最终模板文件。复杂功能通常由设置、管理器、前端控制器、异步接口、资源和定时任务共同构成。
