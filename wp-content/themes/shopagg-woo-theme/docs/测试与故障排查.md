# SHOPAGG 主题：测试与故障排查

## 1. 先确定故障层

```text
浏览器/UI
  -> WordPress 路由、权限、Nonce
    -> SHOPAGG 主题模块
      -> SHOPAGG 主题核心 / WooCommerce / 构建器
        -> 数据库、Cron、文件系统
          -> Web/PHP 主机限制
            -> SHOPAGG/XTemos/媒体远程服务
```

记录“最先失败的一层”。例如 Prebuilt 页面显示红色并不等于导入 JS 有错，可能是附件远程请求在 PHP 侧超时。

## 2. 必备证据

每个故障至少收集：

- 精确后台/前台 URL；
- 操作时间和时区；
- 用户角色；
- 主题、Core、Woo、构建器、SHOPAGG 插件版本；
- PHP/WordPress 版本和内存/执行时间；
- 浏览器 Network 中第一个失败请求及响应；
- PHP fatal/debug log；
- WooCommerce 日志和 Scheduled Actions；
- 相关 option/CPT 的存在性；
- 是否只在缓存/CDN 开启时发生。

分享证据前删除 Token、Nonce、Cookie、邮箱、地址、订单资料和签名 URL。

## 3. PHP 基础检查

开发环境：

```bash
find . -type f -name '*.php' -print0 | xargs -0 -n1 php -l
```

大型主题逐文件检查会较慢，但能发现发布包中的语法错误。还要查看：

- `wp-content/debug.log`；
- PHP-FPM/Apache/Nginx error log；
- 发生 AJAX 500 时对应请求时间；
- PHP extension：curl、zip、dom/xml、mbstring、gd/imagick；
- 文件所有者和权限。

## 4. Prebuilt 导入超时

错误：

> The import could not be completed due to a low timeout limit on the server. You need to contact your hosting provider and ask them to increase it to 300 seconds.

当前导入器已把媒体拆成小批次：每个 `imagesN` 默认处理 3 个附件，单个远程媒体请求超时约 15 秒，响应以 `has_more`/`next_offset` 继续同一阶段。浏览器 AJAX timeout 较长，但浏览器设置不能突破 Nginx、CDN、负载均衡、PHP-FPM 或主机强制中断。

按顺序检查：

1. PHP `max_execution_time` 是否至少 300；
2. PHP-FPM `request_terminate_timeout`；
3. Nginx `fastcgi_read_timeout` / 反向代理 timeout；
4. Apache/主机面板的请求限制；
5. CDN/WAF 的最大请求时间；
6. PHP `memory_limit`、`post_max_size`、磁盘和 inode；
7. 服务器到媒体源的 DNS、SSL、IPv6、出站防火墙；
8. WooCommerce 日志 source `failed-import-images`；
9. Network 响应是 504、524、500 还是 WordPress JSON 错误；
10. 是否某一个远程 URL每次都卡满 15 秒。

主机不能提高单请求上限时，可临时把每批附件降到 1：

```php
add_filter( 'shopagg_import_media_batch_size', function () {
    return 1;
} );
```

此代码放子主题或临时诊断插件。它会增加请求数量，但降低每次请求耗时；如果单个媒体 URL 就无法访问，减小批次不能解决，需要修复媒体源或出站网络。

导入完成条件不能只看 UI：检查 XML 预期商品/附件数量、`_thumbnail_id`、gallery、上传文件、首页、菜单、Header 和构建器数据。完整说明见 [Prebuilt Websites 技术设计](预建网站技术设计.md)。

## 5. Prebuilt 提示成功但图片/商品缺失

### 商品缺失

- 检查当前构建器对应 XML 是否存在；
- 检查 WXR 导入错误、重复 slug/SKU、用户映射；
- 检查 WooCommerce 和 Core 是否启用；
- 检查产品 post 数量与 XML 预期；
- 检查导入完整性响应是否被旧 JS 缓存；
- 检查数据库事务/主机因超时回滚或中断。

### 图片缺失

- 检查远程 `attachment_url` 是否服务器可访问；
- 检查 CDN fallback；
- 检查上传目录可写和磁盘空间；
- 检查 MIME、文件大小、HTTP 状态和实际响应类型；
- 检查 attachment post 与物理文件；
- 检查 metadata 和 `_thumbnail_id` 映射；
- 查看 `failed-import-images` 日志；
- 重试时确认已成功附件能复用，不重复生成。

## 6. 主题插件无法安装

`xts_plugins` 页面背后使用 TGM/主题安装逻辑，来源不完全相同：

| 插件 | 来源 |
| --- | --- |
| SHOPAGG 主题核心 | 父主题 `inc/plugins/shopagg-woo-theme-core.zip` |
| Elementor/WooCommerce/CF7/Safe SVG/MailChimp | WordPress.org（通常） |
| WPBakery | `WOODMART_PLUGINS_URL/js_composer.zip` |
| Image Optimizer | XTemos 远程 ZIP |

排查步骤：

1. 确认当前构建器，插件列表会过滤掉另一构建器；
2. 检查 Core ZIP 存在、可读、结构正确；
3. 检查 `wp-content/plugins` 和 `wp-content/upgrade` 可写；
4. 检查 WordPress 是否要求 FTP 凭证；
5. 查看安装请求响应和 PHP 日志；
6. 测试服务器访问 WordPress.org/XTemos；
7. 检查 ZIP/curl 扩展、磁盘、包大小和 SSL CA；
8. 检查是否已有同目录残留或插件主文件名变化；
9. 检查 SHOPAGG/安全插件是否拦截下载或 upgrader；
10. 手工上传仅用于判断包本身，最终仍要修复正常更新链路。

要完全解除 XTemos 插件源依赖，需要把 WPBakery/Image Optimizer 作为 SHOPAGG 资源发布并修改来源协议。这是产品发布改造，不是简单改 URL。

## 7. 后台菜单重复图标/菜单

- 查看菜单 DOM，确认是伪元素、SVG、img 还是 background 重复；
- 检查 `menu_icon` 和品牌 CSS 是否同时生效；
- 检查 CPT `show_in_menu` 是否归到 `xts_dashboard`；
- 检查子主题/白标/旧定制插件是否也注册菜单；
- 禁用后台缓存并清 OPcache；
- 以无插件冲突方式逐一恢复。

不要仅用 CSS 隐藏重复项；先消除重复注册，否则权限、当前项和无障碍导航仍有问题。

## 8. 更新故障

### 没有更新提示

```bash
wp option get shopagg_app_store_managed_resources --format=json
wp transient delete --all
wp theme list
```

生产环境不要为一个问题无差别删除所有 transient；优先删除 `update_themes` 对应 site transient。再检查服务端 `shopagg-woo-theme` 版本、类型和发布状态。

### 更新后出现两个主题目录

停止继续更新，记录实际目录和活动 stylesheet。检查 ZIP 根目录、managed asset_file 和 source normalization。不要在活动站直接删除任一目录，先在备份环境确认哪个目录含新版本和站点定制。

## 9. 构建器故障

### Elementor 编辑器加载不完

- PHP fatal/内存；
- REST 和 loopback；
- 安全规则拦截；
- 当前构建器不是 Elementor；
- Elementor generated CSS；
- 浏览器控制台首个错误；
- 第三方 widget 冲突。

### WPBakery 元素缺失

- `WPB_VC_VERSION` 是否定义；
- 当前 builder 是否 `wpb`；
- map 文件是否加载；
- shortcode 文件是否存在；
- 插件版本与主题字段兼容；
- 当前页面是否使用 Gutenberg native 模式。

## 10. 数据库与 Cron

```bash
wp option get woodmart_version
wp cron event list
wp action-scheduler action list --status=failed
wp post list --post_type=woodmart_layout --format=count
wp post list --post_type=product --format=count
wp post list --post_type=attachment --format=count
```

Action Scheduler WP-CLI 子命令取决于当前 WooCommerce/扩展是否提供。不可用时从 WooCommerce 后台 Scheduled Actions 查看。

## 11. 故障修复后的验收

- 能稳定复现旧问题，并确认新版本不再复现；
- 没有通过隐藏错误或放宽所有权限“修复”；
- 日志没有新增 warning/deprecated/fatal；
- 对应数据最终状态正确；
- 重试不会重复创建商品、附件、订单或邮件；
- 缓存开关前后都正确；
- 旧版本升级路径和全新安装都测试；
- 记录根因、修复范围、回滚和监控指标。
